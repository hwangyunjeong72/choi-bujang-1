# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 Deploy 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 본인 계정의 Public 저장소인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 2단계에서 실제 저장소와 배포 주소로 맞춥니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다.

## 2단계 — 자료를 서버 함수 뒤로 이동

가상 메모 네 건은 Supabase의 `public.learning_notes` 테이블에 학습용으로 저장합니다. 화면은 `/api/notes` Vercel 서버 함수를 통해서만 자료를 읽습니다.

- 서버 함수는 `SUPABASE_URL`과 서버 전용 `SUPABASE_SECRET_KEY` 환경변수를 사용합니다.
- 서버 전용 키는 브라우저 파일, API 응답, 로그에 넣지 않습니다.
- `public/data.json`을 생성하지 않도록 빌드 흐름을 변경했습니다.
- `/data.json`은 더 이상 가상 메모를 제공하지 않아야 합니다.
- **현재 약점:** `/api/notes` 자체는 아직 공개 주소입니다. 따라서 URL을 아는 비로그인 사용자가 서버 함수에 직접 요청할 수 있습니다. 이후 단계에서 이 공개 API 접근을 보호해야 합니다.

### 확인 방법

1. Vercel 환경변수에 `SUPABASE_URL`과 `SUPABASE_SECRET_KEY`를 설정합니다. 실제 `SUPABASE_SECRET_KEY` 값은 코드나 GitHub에 기록하지 않습니다.
2. `npm run build` 후 Vercel에 배포합니다.
3. `/`에서 가상 메모 카드 네 건이 보이는지 확인합니다.
4. `/data.json`을 직접 열었을 때 네 메모의 제목·본문이 없어야 합니다.
5. 브라우저 개발자 도구의 Network에서 브라우저가 Supabase에 직접 공개 키로 요청하지 않고 `/api/notes`를 요청하는지 확인합니다.
6. `/api/notes` 응답에는 메모 데이터만 있고 서버 전용 키가 포함되지 않아야 합니다.

## 2단계 확인 기록 — 가상 메모 문장 잔존 여부

2단계의 목표는 **현재 공개 배포와 GitHub 최신 파일에서 가상 메모 문장이 정적 공개 자료로 남아 있지 않은지 확인하는 것**입니다.

확인할 가상 메모 문장은 다음 네 개입니다.

- `실습용 가상 과제 기록`
- `실습용 가상 포트폴리오 기록`
- `실습용 가상 리추얼 기록`
- `실습용 가상 행정 기록`

### A. GitHub 최신 파일 검색

GitHub 저장소의 **최신 커밋 기준 파일**에서 위 네 문장을 각각 검색합니다.

1. 저장소의 최신 `main` 화면을 엽니다.
2. 저장소 검색 또는 파일 검색에서 위 네 문장을 한 문장씩 검색합니다.
3. `data.json`, `public/data.json`, `public/index.html`, 기타 정적 파일에 네 문장이 남아 있지 않은지 확인합니다.
4. 검색 결과를 아래 기록표에 남깁니다.

| 검색 문장 | GitHub 최신 파일 검색 결과 | 확인 날짜 |
|---|---|---|
| `실습용 가상 과제 기록` | ____________________ | __________ |
| `실습용 가상 포트폴리오 기록` | ____________________ | __________ |
| `실습용 가상 리추얼 기록` | ____________________ | __________ |
| `실습용 가상 행정 기록` | ____________________ | __________ |

**주의:** 검색 결과가 `0건`이라고 확인되더라도 이것은 **현재 최신 파일에 없다는 뜻**이지, 과거 커밋에서 노출된 적이 없다는 뜻은 아닙니다.

### B. 현재 Vercel 배포 검색

현재 Production 배포에서 공개되는 정적 자료를 확인합니다.

1. 현재 배포의 `/` 화면을 엽니다.
2. 브라우저의 `Ctrl+F`로 위 네 문장을 각각 검색합니다.
3. `/data.json`도 직접 열어 같은 네 문장을 검색합니다.
4. 현재 정적 공개 파일에 메모 문장이 남아 있지 않은지 기록합니다.
5. `/api/notes`는 별도로 확인합니다. 이 주소는 현재 단계에서 **일부러 공개된 서버 함수 주소**이므로, 여기에서 네 메모가 반환되는 것은 현재 약점으로 기록합니다.

### C. 공개 API의 남은 약점 기록

현재 2단계에서는 `/api/notes` 주소가 공개되어 있습니다.

따라서 URL을 알고 있는 비로그인 사용자가 `/api/notes`에 직접 요청할 수 있으며, 서버 함수가 Supabase에서 가져온 가상 메모를 응답할 수 있습니다.

이것은 **2단계에서 아직 해결하지 않은 약점**입니다.

- 공개 API 주소: `/api/notes`
- 현재 상태: 공개 접근 가능
- 반환 자료: 학습용 가상 메모
- 서버 전용 `SUPABASE_SECRET_KEY`: 응답에 포함하지 않음
- 다음 방어 단계의 목표: 공개 API 접근 자체를 보호

### D. 과거 노출에 대한 주의

**옛 공개 GitHub 커밋이나 옛 Vercel 배포가 남아 있는 동안에는 과거 노출이 해소되었다고 쓰지 않습니다.**

현재 최신 파일과 현재 Production 배포에서 네 문장이 사라진 것을 확인하더라도 다음 두 가지는 별개의 문제입니다.

1. 과거 GitHub 커밋에 네 문장이 남아 있을 수 있습니다.
2. 과거 Vercel 배포에서 네 문장이 공개되었을 수 있습니다.

따라서 이번 단계의 확인 결과는 다음처럼 구분해서 기록합니다.

- **현재 Production 배포:** ____________________
- **과거 GitHub 커밋:** ____________________
- **과거 Vercel 배포:** ____________________
- **과거 노출 해소 여부:** 옛 커밋·옛 배포가 남아 있으므로 `해소되지 않음` / 별도 확인 필요

> 현재 공개 상태를 줄였다는 것과 과거에 공개된 자료까지 회수했다는 것은 같은 의미가 아닙니다.
